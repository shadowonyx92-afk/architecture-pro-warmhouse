# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

#### **Управление отоплением:**

**Пользователи могут:**
- регистрировать устройства в системе - **POST /api/v1/sensors**
- просматривать список устройств - **GET /api/v1/sensors**
- получать информацию о конкретном устройстве - **GET /api/v1/sensors/:id**
- изменять параметры устройства (включение/выключение) - **PATCH /api/v1/sensors/:id/value**
- удалять устройства - **DELETE /api/v1/sensors/:id**

**Система поддерживает:**
- хранение устройств в базе данных в таблице sensors
- централизованное управление через сервер - *h.DB.UpdateSensorValue(...)*
- синхронное управление устройствами

#### **Мониторинг температуры:**

**Пользователи могут:**
- просматривать текущую температуру - **GET /api/v1/sensors**
- получать температуру по локации - **GET /api/v1/sensors/temperature/:location**
- получать температуру конкретного датчика - **GET /api/v1/sensors/:id**

**Система поддерживает:**
- температурные датчики - *Temperature SensorType = "temperature"*
- получение данных в реальном времени - *s.HTTPClient.Get(fmt.Sprintf("%s/temperature/%s", s.BaseURL, sensorID))*

### 2. Анализ архитектуры монолитного приложения

**Технологический стек:**
- Язык программирования: Go
- Web-фреймворк: Gin
- База данных: PostgreSQL
- БД-драйвер: pgx
- Контейнеризация: Docker + Docker Compose

**Структура приложения:**
- Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения
- Отсутствует чёткое разделение доменных правил и инфраструктурного кода
- Все запросы обрабатываются синхронно
- Бизнес логика разделена в обработчике (handlers) и в сервисах 
- Архитектура основана на модели request–response
- PostgreSQL используется как единый источник данных

**Файловая структура:**
- **db.go** — вся работа с PostgreSQL, CRUD для устройств
- **handlers/sensor.go** — HTTP API через Gin, обновление данных, интеграция с внешним TemperatureService
- **temperature_service.go** — внешняя интеграция с температурным API
- **model/sensor.go**
- **main.go** — конфигурирует сервер, роутинг, DB, temperature API, health-check

**Плюсы:**
- Простота реализации и понимания
- Минимальные операционные затраты
- Быстрый старт для MVP
- Отсутствие сетевой сложности между внутренними компонентами

### 3. Определение доменов и границы контекстов

#### Домены

##### Управление устройствами
Сюда у нас входит логика создания, обновления, удаления, получения устройств, а также управление значениями и статусом устройств

Контекстом является всё, что связано с управлением сенсорами, включая слой хранения (через db.DB) и слой API (handler/sensors.go). При этом контекст изолирован от внешнего API температуры — любые внешние данные приходят через сервис TemperatureService

Данный домен разбросан по разным файлам:
**models/sensors.go** — описание сущностей для работы с устройствами (Sensor, SensorCreate, SensorUpdate)
**db.go** — реализация CRUD и логики обновления устройств (CreateSensor, UpdateSensor, DeleteSensor, UpdateSensorValue)
**handlers/sensors.go** — обработка HTTP-запросов на управление устройствами (CreateSensor, UpdateSensor, DeleteSensor, GetSensors)

##### Мониторинг температуры
Сюда входит: 
- получение актуальных данных температуры с внешнего источника
- преобразование ответа API в внутренние модели (TemperatureResponse)
- обновление данных устройства в Sensors Context

Контекстом является сервис TemperatureService и внешний API (temperature-api)

Данный домен разбросан по двум файлам:
**services/temperature_service.go** - сервис для получения температуры (GetTemperature, GetTemperatureByID)
**handlers/sensors.go** → обновление значений температурных устройств при GET /sensors или GET /sensors/:id

##### Веб/API
По сути основа приложения. Отвечает за маршрутизацию запросов, валидация входных данных и координацию между доменами **Мониторинг температуры** и **Управление устройствами**

Контекст - это весь код, связанный с обработкой HTTP-запросов и маршрутизацией

Данный домен разбросан по двум файлам:
**main.go** - точка входа, регистрация маршрутов
**handlers/sensors.go** - все обработчики API для устройств

##### БД
Отвечает за сохранение и извлечение состояния устройств из базы

Контекст - это весь код, связанный с доступом к БД

Данный домен разбросан по двум файлам:
**db.go** — репозиторий
**main.go** — инициализация подключения к БД

### **4. Проблемы монолитного решения**

- Отсутствует история изменений данных
- Обновление или изменение функциональности требует пересборки образа и перезапуска всего приложения
- Масштабирование возможно только целиком, без выделения отдельных частей
- Домены живут в одном процессе
- Одна БД используется для всего

На самом деле решение нормальное, простое MVP решение для быстрого старта, чтобы было что показать, как прототип или на каком нибудь демо.

**Диаграмма контейнеров (Containers)**

В отличие от диаграммы контекстов, [тут](./schemas/as_is/container.puml) добавилась еще БД и видно детальнее что входит в монолит. Тут у нас еcть:

##### TO BE

Пришел [к такой упрощенной схеме](./schemas/to_be/container.puml):
- **API Gateway** – единая точка входа, проверка JWT, маршрутизация запросов к сервисам (HTTPS/REST)

- **Device Management Service** – CRUD устройств, управление состоянием и командами, приём данных от внешних устройств (HTTP/MQTT + PostgreSQL)
- **Telemetry Service** – приём, хранение и выдача телеметрии устройств (MQTT/WebSocket + TSDB)
- **Automation Service** – управление сценариями и автоматизация, исполнение команд по событиям (REST/gRPC + Event/Webhook)
- **DeviceDB** – хранение конфигурации и состояния устройств (SQL)
- **AutomationDB** – хранение сценариев и правил автоматизации (SQL)
- **TelemetryDB** – хранение телеметрии устройств (Time Series DB)
- **Partner Devices** – внешние датчики и устройства, предоставляющие данные (HTTP/MQTT)

Можно упороться и сделать еще дательнее, но для начала думаю пойдет

**Диаграмма компонентов (Components)**

##### AS IS

Из за того, что это монолит, [схема](./schemas/as_is/components.puml) тоже выглядит не сложно и очень похожа на предыдущую схему

##### TO BE

Нарисовал три схемы, основные для данного проекта

**[Device Managment Service](./schemas/to_be/components/device_management_service.puml)**

Как можно понять по названию отвечает за работу с устройствами. Состоит из следующих компонентов:
- **Device API Controller** – REST-запросы от API Gateway
- **Device Service** – бизнес-логика управления устройствами
- **Device Repository** – хранение данных устройств
- **Device Adapter Interface** – единый контракт для интеграции с разными устройствами
- **Temperature/Light/Gate Adapter** – конкретные реализации для интеграций с устройствами
- **Event Publisher** – публикация телеметрии и событий
- **Command Listener** – приём команд от Automation Service

**[Automation Service](./schemas/to_be/components/automation_service.puml)**
Отвечает автоматизацию и настройку поведения устройств. Состоит из следующих компонентов:
- **Automation API Controller** – принимает запросы на управление сценариями автоматизации
- **Automation Engine** – выполняет сценарии и решает, какие действия запускать
- **Automation Repository** – хранит сценарии и правила автоматизации
- **Trigger** – запускает сценарии по событиям или расписанию
- **Event Listener** – получает события и телеметрию от других сервисов для обработки

**[Telemetry Service](./schemas/to_be/components/telemetry_service.puml)**
- **Telemetry API Controller** – предоставляет данные телеметрии по запросу.
- **Telemetry Ingestor** – принимает и обрабатывает телеметрию от устройств.
- **Telemetry Repository** – хранит телеметрию в базе данных.
- **Event Publisher** – отправляет события и уведомления для Automation Service

# Задание 3. Разработка ER-диаграммы

[ER диаграмма](./schemas/to_be/er.puml)

На основе C4 и предметной области выделяем следующие ключевые сущности:
- **User** — пользователь экосистемы
- **House** — дом/жильё пользователя
- **Device** — устройство (температура, свет, ворота и т.д.)
- **DeviceType** — тип устройства (Temperature, Light, Gate)
- **Module** — отдельный модуль, комплект устройства или группа. Может объединять несколько устройств
- **Scenario** — сценарий автоматизации (Automation Service)
- **TelemetryData** — телеметрия от устройства
- **Action** — действия, связанные со сценариями

Ниже объяснение связей в диаграмме:
| Откуда   | Куда          | Тип связи | Комментарий                                      |
| -------- | ------------- | --------- | ------------------------------------------------ |
| **User**     | **House**         | 1 → N     | Один пользователь может иметь несколько домов    |
| **House**    | **Device**        | 1 → N     | Один дом может иметь несколько устройств         |
| **Device**   | **DeviceType**    | N → 1     | Каждое устройство относится к одному типу        |
| **Module**   | **Device**        | 1 → N     | Один модуль может объединять несколько устройств |
| **House**    | **Scenario**      | 1 → N     | Сценарии привязаны к дому                        |
| **Scenario** | **Action**        | 1 → N     | Один сценарий может содержать несколько действий |
| **Device**   | **Action**        | 1 → N     | Каждое действие связано с устройством            |
| **Device**   | TelemetryData | 1 → N     | Устройство может генерировать много телеметрии   |


# Задание 4. Создание и документирование API

### 1. Тип API

Тут подходит **гибридное решение**, потому что есть вещи от которых хочешь получить ответ в моменте - синхронные для обновления устройств и асинхронные - для записи истории изменения значений устройства. Тобишь:

- REST — управление и запросы
- Async — телеметрия и события

#### REST API
REST API используется для взаимодействия между API Gateway, Device Management Service и Telemetry Service.

##### Device Management Service
Регистрация нового устройства:
- Метод: POST /devices
- Описание: Регистрирует новое устройство в системе

Отправка команды устройству:
- Метод: POST /devices/{deviceId}/commands
- Описание: Отправляет команду конкретному устройству (например, включение света)

##### Telemetry Service
Получение телеметрии устройства:
- Метод: GET /telemetry/{deviceId}
- Описание: Возвращает последние телеметрические данные устройства

#### AsyncAPI
Асинхронное взаимодействие используется для передачи телеметрии и событий автоматизации

##### Публикация телеметрии
Путь: Device Management Service -> Telemetry Service
Описание: Устройство публикует новые измерения (температура, состояние).

##### Триггер автоматизации
Путь: Telemetry Service -> Automation Service
Описание: При выполнении условий правила инициируется сценарий автоматизации.

### **Что нужно сделать**

[Переходная схема](./schemas/transition/container.puml)

Суть такая, что мы монолит трогаем минимально: 
- для начала добавляем новое решение в виде Device Management Service (DMS) в котором будет располагаться новая логика работы с новыми сервисами и телеметрией
- БД тоже пока что общая, не будем усложнять разделением
- для новых сервисов заводим новые таблицы, старая пусть живет ожидая миграции
- Внутрь монолита добавляем DMS который будет работать с уже новыми датчиками, а работа со старыми будет осуществляться точно также
- Проверять новый датчик или нет, будем проверять по записям в БД
- эндпоинты монолита остаются теже самые, просто ведут в разные сервисы в зависимости от того, новое устройство или нет
- любые изменения мы записываем в телеметрию, делаем только для новых датчиков, старые автоматические ее получат, как съедут из монолита
- в будущем будет не сложно добавлять новые датчики, сразу будет работать телеметрия для них
- монолит в будущем превратиться в точку входа API Gateway c минимальным количеством логики
